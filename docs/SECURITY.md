# Security

## Controls in place

**Authentication and sessions**
- Passwords hashed with scrypt by Better Auth; minimum length 10.
- Sessions stored in the database, delivered in HTTP-only, `SameSite=Lax` cookies, `Secure` when the site address is HTTPS.
- Password reset tokens are single-use and expire after one hour; a reset signs out every other session.
- Optional mandatory email verification (`REQUIRE_EMAIL_VERIFICATION=true`).
- Sign-in errors do not say whether the email or the password was wrong; the reset form gives the same answer for known and unknown addresses.
- Database-backed rate limits on sign-in, sign-up and password reset (active in production), and on the contact form, uploads, discussion posts, content reports and certificate verification.

**Authorization**
- Role, suspension and permissions are read from the database on every request. The role cannot be set through registration or profile updates.
- Every mutation and every read goes through a service that checks the acting user. Layout redirects and hidden buttons are conveniences, not controls.
- Course operations additionally require membership of that course's teaching team.
- Records belonging to someone else are reported as "not found".
- Sensitive administrator actions require the administrator's password again and are written to the audit log.
- The last active administrator cannot be demoted or suspended; nobody can change their own role or suspend themselves.

**Input and output**
- All input is validated on the server with Zod. Database access is through Drizzle's parameterised queries; search terms are escaped for `LIKE`.
- React escapes output. Lesson and description content is Markdown rendered without raw HTML.
- CSV exports neutralise spreadsheet formula injection.
- Server actions are protected by the framework's origin check; the upload route handler checks the `Origin` header itself.
- Security headers: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security`.

**Files**
- Upload authorization, size limit, extension allow-list and a content-signature check all happen on the server. The stored content type is derived from the extension, never taken from the browser. Scripts, HTML and SVG are refused.
- Storage keys are generated by the server. Downloads are authorized per request and served through short-lived signed URLs (or streamed, in local development). Types a browser might execute are forced to download.

**Assessments**
- Correct answers, accepted answers and explanations are never included in what is sent to a learner during an attempt.
- Time limits, availability windows and attempt limits are enforced on the server. Scores are calculated on the server.
- Results stay hidden until released under the assessment's policy.

**Payments**
- Enrollment is activated only inside the same database transaction that marks a verified payment as succeeded. Callbacks are authenticated, confirmed with the provider, and applied exactly once.

**Operations**
- Secrets come only from environment variables and are never shown in the settings pages.
- Unexpected errors are logged on the server; users see a generic message.
- `/api/health` reveals component detail only with a bearer token.

## Known limitations

Stated plainly so that nobody relies on something that is not there.

1. **No two-factor authentication.** Step-up for sensitive actions is password re-entry only. Better Auth has a two-factor plugin that can be added.
2. **Registration reveals whether an email is already registered** when email verification is off, because the form says so. Turning on `REQUIRE_EMAIL_VERIFICATION` removes this.
3. **No Content-Security-Policy header.** The app does not render untrusted HTML, but a CSP would be a useful extra layer. It needs nonce support for the framework's inline scripts and was not added.
4. **No malware scanning of uploads.** Files are checked for type and signature, not for malicious content. Treat downloaded submissions with normal caution, or add a scanning step in front of storage.
5. **Uploaded files are served from the application's own origin in local-storage mode.** In production (S3) they are served from the storage provider's origin through signed URLs.
6. **Examinations are not proctored.** The platform enforces timing, attempts, randomisation and answer secrecy. It cannot stop a learner from using another device, another person or other materials, and it does not claim to.
7. **M-Pesa callbacks are not signed by Safaricom.** The integration relies on a secret callback path plus a server-to-server status query. It has not been run against live Daraja.
8. **Refunds do not move money.** Approval records the decision and removes access.
9. **Certificate PDFs use standard fonts**, which cover Latin characters. Names in other scripts are transliterated or replaced with `?`. Embedding a Unicode font would fix this.
10. **Expired attempts are closed lazily**, when the learner or instructor next looks, rather than by a scheduled job. The result is the same; only the moment of closing differs.
11. **Rate limits are per key in fixed windows.** They slow abuse; they are not a substitute for network-level protection against a determined flood.
12. **The audit log is append-only at the application level.** A database administrator can still alter it. Restrict direct database access accordingly.
13. **Dependency audit.** On 12 October 2026 `npm audit` reported 13 advisories (9 high, 4 moderate), all in build and development tooling rather than in code that handles requests: the file-globbing library `braces`/`micromatch` reached through `eslint-config-next` and the `shadcn` CLI, and the `esbuild` development server reached through `drizzle-kit`. None has a non-breaking fix available yet. `shadcn` is listed under `dependencies` only because the stylesheet imports its CSS at build time. Re-run `npm audit` before each release and update when fixes land.

## Data retention and deletion

- Learners can request deletion from **Account settings**. An administrator completes it from the user's page, which anonymises the account and removes profile data, credentials, sessions, notes, bookmarks and notifications.
- Grades, certificates and payment records are retained against the anonymised account so that certificates remain verifiable and financial records stay complete.
- There is no automatic purge of old data. Decide a retention period that fits your obligations and apply it.

## Reporting a vulnerability

Contact the platform operator through the support address configured in **Admin > Settings**. Do not open a public issue for a security problem.
